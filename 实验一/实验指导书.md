# 实验一：RISC-V 引导与裸机启动

## 一、实验概述

本实验面向大三上学生，目标是帮助学生从“操作系统如何被启动”这一问题出发，理解最小内核从上电到输出第一条调试信息的完整路径。实验内容围绕 RISC-V 架构、QEMU 模拟器、链接脚本、启动入口代码和串口输出展开。

与常见的 Linux 用户态程序不同，本实验中的程序运行在裸机环境中，没有现成的运行时库、没有操作系统负责装载程序、也没有默认初始化好的栈和输入输出接口。因此，学生需要亲手处理程序入口、内存布局、栈初始化和串口输出等关键问题，从而建立对操作系统启动过程的直观认识。

本实验所用源代码请参考仓库 `https://github.com/Riptide65536/Whu-OSlab` 的 `lab1` 分支。

## 二、实验目标

完成本实验后，学生应当能够：

1. 理解最小操作系统的引导过程，知道内核从入口代码开始是如何逐步运行起来的。
2. 理解裸机程序与普通 Linux 用户态程序在地址空间、程序入口和运行环境上的区别。
3. 初步掌握链接脚本的作用，能够通过自定义链接地址让程序被放置到正确的物理内存位置。
4. 理解启动代码中设置栈指针 `sp` 的必要性，并能分析未设置栈时程序为何无法正常运行。
5. 理解串口 `UART` 的基本用途，能够在 QEMU 中输出启动信息和测试信息。
6. 通过额外任务建立对“锁”的初步认识，理解锁在操作系统中的基本作用。

## 三、前置知识

在开始本实验前，建议学生具备以下基础：

1. 能够使用 `make` 完成代码编译，理解目标文件、可执行文件和链接的基本概念。
2. 具备基础的 C 语言与 RISC-V 汇编阅读能力。
3. 能够完成 QEMU 的基本启动，知道如何运行和退出 QEMU。
4. 了解 GDB 的基本使用方式，例如设置断点、单步执行、查看寄存器和反汇编。

建议配套提供以下前置阅读材料：

1. QEMU 基本使用说明。
2. GDB 基本使用说明。
3. 链接脚本的入门介绍。
4. 相关参考实验或 xv6 启动流程简介。

## 四、实验环境与普通程序的区别

学生在本实验中最容易产生的误解是：既然都是“编译后运行”，为什么裸机程序还需要额外关心入口、地址和栈？

这是因为普通 Linux 用户态程序和裸机程序所处的运行环境完全不同。

### 1. 普通 Linux 用户态程序

对于普通程序，操作系统会负责：

1. 创建进程地址空间。
2. 把程序装载到合适的虚拟地址。
3. 初始化栈、堆和运行时环境。
4. 提供标准输入输出和系统调用接口。
5. 在程序退出后回收资源。

因此，用户态程序通常只需要从 `main` 函数开始编写逻辑，而不需要自己关心程序最初是如何被放到内存中的。

### 2. 裸机程序 / 最小内核

在裸机环境中：

1. 没有现成的操作系统帮你装载程序。
2. 没有默认初始化好的栈。
3. 没有标准库帮助你完成输入输出。
4. 程序必须从指定入口地址开始执行。
5. 程序所放置的内存位置必须与 QEMU 或硬件平台的预期一致。

因此，内核启动时首先面对的问题不是“算法如何写”，而是“CPU 第一条执行的指令在哪、栈在哪、输出设备在哪”。

### 3. 需要重点理解的差异

本实验建议围绕以下三个差异展开讲解：

1. 地址空间不同：普通程序依赖操作系统提供的虚拟地址空间，裸机程序更多直接面向物理地址或固定映射地址。
2. 程序开始位置不同：普通程序通常从运行时入口间接进入 `main`，裸机程序则从链接脚本指定的入口开始执行。
3. QEMU 中 RAM 的位置不同：程序必须被放到 QEMU 允许 CPU 正确取指和访问的位置，否则即使编译成功也无法运行。

## 五、链接脚本与程序装载地址

### 1. 为什么需要链接脚本

编译器负责把每个源文件翻译为目标文件，而链接器负责把多个目标文件合并成最终可执行文件。链接脚本的作用，是告诉链接器：

1. 程序的入口符号是什么。
2. 代码段、数据段、只读段和未初始化段如何排列。
3. 这些段最终应当被放到什么地址。

在普通程序开发中，这些细节通常由默认链接规则自动完成；但在内核或裸机程序中，链接脚本往往是必须手工控制的。

### 2. 一个简单的过渡性理解

建议先给学生展示一个“在 Linux 上自定义程序地址布局”的简单例子，让学生知道：

1. 程序的节区布局并不是固定不变的。
2. 链接器可以按照脚本要求重新放置代码和数据。
3. 程序能否运行，与它被放到哪里密切相关。

之后再引导学生理解：在裸机环境中，这种“放到哪里”的问题不再只是调试技巧，而是程序能否启动的基本前提。

### 3. 本实验中的核心要求

学生需要理解并回答以下问题：

1. 为什么内核不能随意链接到一个地址？
2. QEMU 启动后，CPU 会从什么位置开始取指？
3. 如果链接地址错误，会出现什么现象？
4. 如何通过自定义链接脚本，把程序放到能正常运行的位置？

## 六、启动过程分析

本实验的核心是理解最小系统的启动链路。建议学生把启动过程看作下面几个连续阶段。

### 1. CPU 从入口地址开始执行

当 QEMU 启动后，CPU 并不是从 `main` 函数开始执行，而是从预设入口位置开始取指。此时系统还没有完成任何高级语言层面的初始化工作。

### 2. 入口汇编代码完成最低限度初始化

在这个阶段，通常需要由 `start.S` 一类的汇编文件完成以下工作：

1. 设置栈指针 `sp`。
2. 根据需要初始化少量寄存器。
3. 跳转到后续的 C 语言入口函数。

### 3. 为什么一定要先设置 `sp`

这是本实验中的重点问题之一。

C 语言函数调用普遍依赖栈来保存返回地址、局部变量和部分寄存器现场。如果在进入 C 代码之前没有设置好 `sp`：

1. 函数调用可能覆盖未知内存区域。
2. 返回地址和局部变量无法被正确保存。
3. 程序很可能立刻异常、死循环或行为不可预测。

因此，“先设栈，再进入 C”并不是某种编码习惯，而是启动阶段的必要条件。

### 4. 从汇编过渡到 C

当最基本的执行环境建立完成后，程序才会跳转到 C 函数，继续执行更高层的初始化逻辑，例如输出启动信息、初始化设备、执行测试代码等。

## 七、串口与调试输出

### 1. 为什么启动阶段常用串口

在操作系统启动初期，图形界面、文件系统和复杂驱动通常都还没有准备好。此时如果希望观察程序是否成功运行，最直接的方式就是使用串口输出调试信息。

串口的优点包括：

1. 接口简单，适合早期启动阶段使用。
2. 便于在 QEMU 中重定向到终端，直接观察输出。
3. 能帮助开发者快速定位程序是否执行到了某一步。

### 2. 本实验中的串口任务

学生需要学习：

1. 什么是 `UART`。
2. 如何向串口寄存器写入字符。
3. 为什么只有在串口初始化正确后，终端中才会看到输出。
4. 如何利用串口输出观察系统是否已经成功进入目标代码路径。

### 3. 实验结果要求

本实验应至少能够在 QEMU 中输出：

1. 启动阶段提示信息。
2. 指定测试信息。

如果程序能够稳定输出预期信息，通常说明入口、栈和串口路径已经基本打通。

建议学生按照如下顺序完成实验：

1. 阅读实验目标和基础背景，明确本实验要解决的问题不是“写一个应用程序”，而是“让一个最小系统真正跑起来”。

3. 阅读链接脚本，弄清程序入口、代码段和数据段的放置位置。
4. 阅读 `start.S` 或对应入口代码，理解其最小初始化逻辑。
5. 分析 `sp` 的设置位置和栈空间来源。

7. 编译并运行程序，观察 QEMU 输出结果。

## 十、调试建议与常见问题

### 1. 程序没有任何输出

可能原因包括：

1. 程序入口地址错误，CPU 没有执行到目标代码。
2. 串口尚未正确初始化。
3. 程序在进入串口输出逻辑前就已经异常。
4. 栈未正确设置，导致函数调用失败。

### 2. 程序卡在入口阶段

建议重点检查：

1. 链接脚本中的入口符号是否正确。
2. 程序是否被链接到 QEMU 允许执行的位置。
3. 启动汇编是否完成了必要跳转。

### 3. 进入 C 代码后行为异常

建议重点检查：

1. `sp` 是否指向一段合法且可写的内存。
2. 栈空间是否足够。
3. 是否错误访问了尚未初始化的全局数据。

### 4. 输出乱码或没有完整输出

建议重点检查：

1. 串口寄存器配置是否正确。
2. 输出函数是否按字符逐个发送。
3. 是否在串口尚未准备好时连续写入。

## 十三、实验总结

本实验是操作系统课程中非常关键的入门实验。它并不追求复杂功能，而是帮助学生跨过“从应用程序思维转向系统程序思维”的第一道门槛。学生一旦真正理解了入口、链接地址、栈初始化和串口输出的关系，后续再学习中断、异常、进程、虚拟内存和设备驱动时，就会更容易建立完整的系统视角。

如果能够顺利完成本实验，学生应当已经具备分析一个最小内核如何启动、如何建立最基本运行环境、以及如何输出调试信息的能力。这将为后续实验打下重要基础。
